# Phase 4a benchmarks

Generated by `scripts/bench-report.mjs` from `docs/benchmarks/phase4a-*.json` (`npm run bench`).

Each tier runs the shell's orogen pipeline (stages 1-5 and 8) in the engine worker through the real app path, one fresh page per tier, seed 12345, debug layers off.

- **generation** is the sum of the six stage durations measured from progress events; **total** also includes transferring the mesh, building the globe and painting the first layer.
- **working set** is the logical size of mesh and layer arrays in the worker (every browser).
- **peak RSS** is the peak resident memory of all processes started from the Playwright browser install, sampled with `ps` every 100 ms (macOS and Linux). It covers page, worker and helpers, and includes the browser's own baseline (shown as the second figure).

## Measurement notes (2026-10-13)

- **Machine.** A 4-core Linux x64 cloud VM (Xeon 2.8 GHz, 16 GB, no GPU), not a desktop. Rendering is software WebGL (each browser's own fallback; the renderer was not recorded). Generation runs in the engine worker on the CPU, so the generation figures are representative of this CPU; the globe and paint figures in "total" are not representative of a machine with a GPU. Phase 1's numbers came from an 18-core Apple-silicon Mac and are not comparable.
- **Firefox** refuses WebGL headless on a GPU-less machine (driver blocklist), so it was run headed on a virtual display: `xvfb-run -a scripts/node24.sh npx playwright test -c playwright.bench.config.ts --project=firefox --headed`. Chromium and WebKit ran headless with `npm run bench`.
- **Peak RSS** sums every process started from the Playwright browser install, sampled every 100 ms. The baseline is sampled when a tier starts and can include processes left over from the previous tier, so "above baseline" is approximate; for WebKit at 200k the baseline even exceeds the peak.
- **Reading the budget.** §6.2 budgets the working set (mesh and layer arrays), and that is within budget at every tier, at the top edge for 2.56M (607 MB vs ~400–600 MB). At 2.56M, real process growth above baseline is 2.1–2.3× the working set (1.25–1.39 GB), likely from copies across the worker transfer, globe geometry and software-rendered GPU buffers (not yet broken down). Below 2.56M the ratio is dominated by baseline noise and is not meaningful. Reducing that is later work and must not lower output quality (REQUIREMENTS, Realism and performance).
- **Where the time goes.** `orogen.climate` is the slowest stage at every tier in every browser, and its share grows with size: 42–46% of generation at 50k, 66–71% at 2.56M.
